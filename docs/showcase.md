## Відтворювана демонстрація

```bash
make demo
```

Потрібні uv, Make і запущений Docker із Compose 2.24.4+.
Перший запуск може завантажувати залежності й образи; `make init` не потрібний.
Demo створює окремий `hw03-demo-*` Compose-проєкт, випадкові секрети, вільні loopback-порти
й власні volumes. Робочий `.env`, робочі бази та їхні дані не використовуються.

PostgreSQL починає з Alice, Bob, Carol і чотирьох завдань. Скрипт виконує справжній
`queries.sql`, включно з BEGIN/COMMIT і змінами даних, та показує номер, пояснення,
назви колонок і результат кожного запиту. Після запитів 3, 5, 7 і 9 змінено по одному рядку.
У запиті 10 статуси `new`, `in progress`, `completed` мають відповідно 2, 2, 0 завдань;
у запиті 14 користувачі мають 2, 2, 0 завдань. Це демонструє й нульові групи LEFT JOIN.

MongoDB додає три початкові документи, створює `simba`, знаходить його, змінює вік
з 1 на 2 та двічі додає `рудий`. Характеристика залишається одна. Потім видаляється
`simba`, показуються інші три коти, видаляються всі й виводиться порожній список.
Усі операції викликають функції з `main.py`. Документи мають справжні ObjectId;
у демонстрації показано лише стабільні поля `name`, `age`, `features`.

Кожен запуск має однакові дані й текст результатів. Навчальний `seed.py` і далі
генерує випадкові дані Faker. Обидва сценарії мають окреме призначення.
Після завершення або звичайної помилки runner виконує cleanup власного проєкту.
Ctrl+C повертає код 130 після спроби cleanup. Якщо Docker не дозволив cleanup,
конфігурація й секрети зберігаються; stderr показує шлях для відновлення.
SIGKILL або вимкнення машини не гарантують cleanup;
див. [аварійне прибирання](operations.md#аварійне-прибирання-тимчасового-проєкту).

## Експеримент з індексами

```bash
make benchmark
# Менший набір / інша кількість повторів:
uv run --locked python -m scripts.benchmark --rows 10000 --repeats 7
```

Працює лише тимчасова PostgreSQL у `hw03-benchmark-*`. Стандартні обсяги —
30 і 100 000 завдань; додаткова велика вибірка налаштовується від 30 до 1 000 000.
Користувачів від 10 до 1000; розподіл завдань між ними циклічний. Статус `new`
мають завдання з номером, кратним 100, і перше завдання. Опис має 128 символів.
Це синтетичні, детерміновані дані з рідкісним `new`; інший розподіл може дати інші плани.

Вимірюються **незмінені запити 1 і 2 з `queries.sql`**, включно з ORDER BY.
Скрипт читає нумеровані секції файлу, без поділу SQL за крапкою з комою всередині рядків.
Базове вимірювання вже містить індекси PRIMARY KEY та UNIQUE. Потім додаються:

```sql
CREATE INDEX tasks_user_id_id_idx ON tasks (user_id, id);
CREATE INDEX tasks_status_id_id_idx ON tasks (status_id, id);
```

Перший стовпець відповідає фільтру, другий — порядку `id`. Це кандидати для експерименту;
вони існують лише у тимчасовій базі й не змінюють навчальну схему.

Методика: ANALYZE після наповнення, один непротокольований EXPLAIN warm-up для кожного
запиту й фази, потім п'ять вимірювань `EXPLAIN (ANALYZE, BUFFERS, SETTINGS, FORMAT JSON)`.
Кількість вимірювань можна змінити від 3 до 30. Planner працює зі штатними налаштуваннями;
послідовне сканування не вимикається. Для малого набору воно може бути правильним вибором.
Результати SELECT порівнюються за кількістю рядків і SHA-256 до/після індексів.

Кожен успішний запуск створює новий каталог `artifacts/benchmarks/<UTC>/`:

- `results.json`: усі плани й вимірювання, SQL, hashes, версія сервера, kernel,
  параметри planner, Python/platform, Compose images і розміри індексів;
- `summary.md`: медіани server execution time й shared hit + read blocks.

Buffers беруться з кореня плану, який уже враховує дочірні вузли.
Це кількість звернень до shared buffers, а не число унікальних сторінок чи фізичних читань.
Час містить overhead EXPLAIN ANALYZE, але не передачу рядків клієнту.
Вимірювання використовують прогрітий кеш; базова фаза завжди передує фазі з індексами.
Навантаження машини, статистики ANALYZE й кеш впливають на результат.
Індекси займають місце та додають роботу під час записів; write throughput тут не вимірюється.

Звіт публікується після успішного cleanup. Тести перевіряють коректність результатів
і наявність планів, без порогів швидкодії й вимоги конкретного scan node.
Методика спирається на документацію PostgreSQL:
[Using EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html) та
[EXPLAIN](https://www.postgresql.org/docs/17/sql-explain.html).

### Фактичне вимірювання — 2026-10-17

Percona PostgreSQL 17.11.1, arm64, п'ять вимірювань у кожній фазі:

| Tasks | SQL | Rows | Before ms | After ms | Buffers до → після |
| --- | --- | --- | --- | --- | --- |
| 30 | 1 | 3 | 0,007 | 0,006 | 1 → 1 |
| 30 | 2 | 1 | 0,008 | 0,006 | 2 → 2 |
| 100 000 | 1 | 100 | 3,457 | 0,044 | 2326 → 102 |
| 100 000 | 2 | 1001 | 5,914 | 6,128 | 2602 → 2602 |

На 30 завданнях обидва запити зберегли Seq Scan. Для великого набору запит 1 перейшов
від Seq Scan до Bitmap Index Scan + Bitmap Heap Scan; Sort залишився.
Запит 2 в обох фазах використовував `tasks_pkey` для порядку `id` та відфільтрував
98 999 рядків. Його оцінка — 33 333 рядки, фактичний результат — 1001.

План містить `status_id = (InitPlan 1).col1`. Наше пояснення: planner не знає конкретного
значення статусу з підзапиту під час оцінювання селективності; оцінка близька до третини
таблиці. Новий індекс статусу не був обраний і не зменшив buffers. Невелика різниця часу
не доводить ні прискорення, ні регресії. Обидва додані індекси займають по 2 260 992 bytes.
Для цього workload доказ користі є лише для індексу користувача.
Запит 2 з підзапитом залишено відповідно до умови завдання.

Повні докази: `artifacts/benchmarks/20261017T001858614098Z/results.json` і `summary.md`;
лог: `artifacts/benchmark-showcase-final-2026-10-17.log`.
Значення вище описують цей запуск, а не гарантію для іншого середовища.
Каталог `artifacts/` ігнорується Git і відсутній у свіжому checkout;
власний звіт із планами створює `make benchmark`.

## Конкурентні записи

```bash
make test-concurrency
```

Вісім сценаріїв працюють зі справжніми Percona серверами:

| Сценарій | Очікуваний результат |
| --- | --- |
| Два INSERT одного email, три раунди | Один запис; UniqueViolation; повний rollback програвшого |
| Два Create одного імені кота, три раунди | Один документ; один DuplicateKeyError |
| Одночасний `$addToSet` однакового значення | Одна нова характеристика |
| Одночасний `$addToSet` різних значень | Обидві характеристики збережені |

Кожен клієнт має окреме з'єднання. Barrier синхронізує старт операцій після підключення;
блокування й переможця визначає база. Перевіряються кінцеві дані після завершення обох
операцій, незалежно від переможця й порядку елементів масиву. Barrier, futures і драйвери
мають timeout. Це перевірка конкретних конфліктів запису, а не load test.
Документація оператора:
[$addToSet](https://www.mongodb.com/docs/v8.0/reference/operator/update/addtoset/).
